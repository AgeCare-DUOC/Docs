## 2. Semana 1 — Planeación y Reorganización del Backlog

### 2.1 Diagnóstico Inicial

Al inicio del Sprint 2, el estado del Product Backlog era crítico:
- 100 issues en Jira: 25 finalizados (mayormente frontend-only con mocks), 4 en progreso, 71 no iniciados.
- Las historias del Sprint 1 no incluían subtareas de backend, base de datos ni infraestructura.
- El profesor de DUOC UC advirtió: *"Centrarse primeramente en los issues más relevantes para el negocio."*

### 2.2 Reflexión como Scrum Master

Mi primera acción fue facilitar una sesión de **Sprint Planning / Backlog Refinement** para reorganizar completamente el backlog. Aplicé el principio de **Vertical Slicing ("tipo torta")**:

> Una Historia de Usuario debe atravesar todas las capas técnicas necesarias para entregar valor observable al usuario final (UI + API + DB). No se permiten épicas técnicas horizontales.

**Decisiones clave tomadas:**
1. No crear nuevas épicas para backend; usar las existentes (DAC05-98 Auth, DAC05-99 Pacientes, DAC05-100 Vitals, DAC05-101 Medicamentos).
2. Todo el desarrollo backend se registra como subtareas dentro de cada Historia vertical.
3. El bootstrap inicial (FastAPI, Docker, asyncpg, Bicep base) se asocia a DAC05-97 (Fundaciones e infraestructura) como Technical Enabler.

**Sprint Goal definido:**
> *"Un familiar puede autenticarse con credenciales reales, ver el perfil de su paciente con datos persistidos, y consultar los signos vitales con un semáforo de bienestar en tiempo real."*

**Historias comprometidas (32 puntos Fibonacci):**
| Historia | Clave | Puntos | Enfoque |
|----------|-------|--------|---------|
| Bootstrap FastAPI + PostgreSQL | DAC05-111 | 3 | Base operativa backend/DB |
| Autenticación Real E2E | DAC05-5 (refactor) | 8 | Backend + Frontend integración |
| Perfil Paciente E2E | DAC05-6 (refactor) | 5 | Backend + Frontend integración |
| Semáforo de Bienestar E2E | Nueva | 8 | Core value — vitales reales |
| Gestión Básica de Medicamentos E2E | Nueva | 8 | Core value — adherencia |

### 2.3 Reflexión como Desarrollador Backend

Durante la primera semana me enfoqué en el **bootstrap del backend** (DAC05-111 y sus 10 subtareas técnicas):

- **Configuración centralizada:** `core/config.py` con pydantic-settings, cargando variables de entorno sin secretos hardcodeados.
- **Conexión async:** SQLAlchemy con asyncpg y sessionmaker asíncrono para operaciones no bloqueantes.
- **Modelos de dominio:** User, Patient, Vital, Medication, ScheduledDose, Alert con relaciones adecuadas.
- **Alembic async:** Entorno `env.py` configurado para migraciones asíncronas en PostgreSQL.
- **Schemas Pydantic v2:** Validación de entrada/salida para todos los endpoints.
- **Endpoints REST:** Auth (register/login/refresh), Pacientes (CRUD), Vitales (registro/consulta/latest), Medicamentos (CRUD/dosis/programación).
- **Middleware RBAC:** Extracción de user_id y roles desde JWT para autorización granular.
- **Manejo de excepciones:** Middleware global estandarizado de errores HTTP.
- **OpenAPI:** Documentación automática en `/docs` para facilitar el consumo del frontend.

**Desafío técnico:** Configurar Alembic para trabajar de forma asíncrona con asyncpg requirió investigación y pruebas iterativas. La solución final utiliza `run_async_migrations` con `engine` asíncrono.

## 3. Semana 2 — Implementación Vertical y Integración

### 3.1 Reflexión como Desarrollador Frontend

En la segunda semana me enfoqué en conectar el frontend Flutter con los endpoints reales del backend, reemplazando los mocks del Sprint 1:

- **Autenticación real:** `AuthRepository` conectado a `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`. Almacenamiento seguro de tokens con `flutter_secure_storage`.
- **Gestión de pacientes:** `PatientsRepository` conectado a `POST /api/v1/patients`, `GET /api/v1/patients`, `PATCH /api/v1/patients/{id}`.
- **Semáforo de bienestar:** Pantalla de inicio con semáforo (ok/warning/attention) consumiendo `GET /api/v1/patients/{id}/wellbeing` y `GET /api/v1/patients/{id}/vitals/latest`.
- **Gestión de medicamentos:** Formulario de alta, agenda diaria con cuenta regresiva, tarjeta de adherencia consumiendo endpoints de medicamentos y dosis.
- **Arquitectura:** Clean Architecture por feature con Riverpod para gestión de estado y go_router para navegación protegida.

**Desafío técnico:** El manejo de expiración de tokens JWT requirió implementar un interceptor HTTP que renueve automáticamente el access token usando el refresh token al detectar un 401, sin cerrar la sesión del usuario.

### 3.2 Reflexión como Scrum Master (continuación)

Durante la segunda semana facilité las ceremonias restantes del Sprint:

- **Daily Scrum:** 15 minutos diarios con las 3 preguntas clásicas. Registro transparente de impedimentos en Jira.
- **Sprint Review:** Demo funcional del flujo end-to-end: registro → login → creación de paciente → registro de vitales → visualización semáforo → gestión de medicamentos. Presentado ante stakeholders de Alloxentric y docentes de DUOC UC.
- **Sprint Retrospective:** Dinámica Glad/Sad/Mad con definición de 1 compromiso de mejora para Sprint 3.

**Impedimentos gestionados:**

## 4. Aprendizajes Clave

### 4.1 Sobre Vertical Slicing
El cambio de historias solo-frontend a historias end-to-end fue el aprendizaje más importante del Sprint 2. Una historia que solo entrega UI con mocks no brinda valor real al usuario. Cada historia debe incluir subtareas de DB, backend y frontend para ser considerada completa.

### 4.2 Sobre el rol tri-fold (Backend + Frontend + Scrum Master)
Operar en tres roles simultáneamente requiere una gestión de tiempo estricta. Los momentos de mayor presión fueron:
- Facilitar ceremonias mientras se desarrollaba código crítico.
- Revisar PRs de compañeros mientras se implementaban propias funcionalidades.
- Mantener el enfoque en el Sprint Goal ante solicitudes de scope creep.

**Estrategia que funcionó:** Bloques de tiempo dedicados (mañana para desarrollo, tarde para Scrum Master, bloqueos sin interrupciones para código complejo).

### 4.3 Sobre Calidad de Software
La definición de «Hecho» (DoD) no es negociable. Una historia no se considera Done si no tiene:
- Criterios de aceptación BDD verificados.
- Pruebas unitarias/integración en verde.
- Análisis estático limpio (`flutter analyze` / `ruff`).
- Trazabilidad Git-Jira completa.
- PR aprobado por peer review y mergeado en `main`.

### 4.4 Sobre Comunicación con Stakeholders
La triangulación entre Alloxentric (empresa), DUOC UC (academia) y el equipo requiere traductor constante. Los requerimientos de negocio de Alloxentric deben traducirse en historias de usuario con criterios de aceptación verificables, y los entregables académicos de DUOC UC deben documentarse con el mismo rigor que el código.

4. **WebSocket:** Implementar notificaciones en tiempo real para alertas críticas.
